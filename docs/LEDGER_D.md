# DEVIATIONS & DISCOVERIES LEDGER — volume D (DD-001…)

> **Append-only retrieval storage.** Append rows at the bottom in sequence; never move,
> renumber, summarize, or delete them. Search by topic or identifier rather than reading a
> volume whole. Code and fixtures settle current behavior; a stale row remains historical.
>
> **Rows are immutable.** The ` [cited]` marker is metadata and may be synchronized in place.
> Otherwise correct a detail with a new row and append `Corrected by D-NNN.` to the old row, or
> replace its whole conclusion with a new row and append `Superseded by D-NNN.` The first pointer
> is final. The guard checks pointer form, not whether the chosen verb is honest.
>
> **Authoring.** Search the volume chain before appending. Write the smallest self-contained
> durable lesson; route debugging narrative to history and point to it from the STATE changelog.
> `LEDGER_ROW_SENTENCE_CAP` and `LEDGER_ROW_CHAR_CAP` are rejection boundaries for new rows.
> Crossing either rejects the row; passing them proves no more than absence of obvious oversizing.
> Boundaries determine when machinery intervenes, not how much content an author should produce.
>
> **Rollover.** `LEDGER_LINE_CAP` is a rollover boundary: the final row may finish after it, but
> a later row starts the next volume. The suffix advances as an A–Z odometer, and existing rows
> never move. The live volume's byte size is measurement only: it is reported but never judged.
> Boundaries determine when machinery intervenes, not how much content an author should produce.
>
> **Paths in rows.** A row's immutability covers its text, not the lifetime or location of a file
> it names. A new path reference must resolve in the tree where the row is authored; a committed
> row's target may later move or disappear, and that drift leaves the historical text alone.
> Append a correction pointer only when meaning changed, and update editable documentation —
> including this preamble — to follow the target. New nonexistent paths are still rejected.
>
> **Citations.** Bare ledger IDs resolve through the volume chain. A row cited from configured
> code or workflow scan paths carries ` [cited]`; the ladder checks that marker in both
> directions. Documentation mentions are intentionally outside that machine check.

- DD-004 [cited]: **A ledger row's immutability covers its text, not the lifetime or location of a file it names.** Reading a committed citation as a retention rule for another tier's file kept a completed plan out of the archive for two releases, and 13.0.0's exemption tested the reference and the target at HEAD, so it survived only until the removal was itself committed. A parentless introducing commit — a shallow boundary or a squash import — settles nothing, so the guard falls back to the default-branch baseline and then to an explicit WARN rather than reporting an unread history as author-time proof or as a newly broken path. Editable prose follows a target that moves, ledger preambles included, and new rows still may not cite a plan's path, because a plan is provisional context whose citation dies when it retires.
- DD-005 [cited]: **A frozen tier must be excluded from path scanning, or it inherits the trap immutability just escaped.** `scripts/guards/path-refs.sh` scanned docs/history/ while the archive's own README and AMH P2 forbid editing what is in it, so a path named in an archived document that later moved could only be repaired by an edit the rules prohibit. The exclusion mirrors the plan tier's, which exists because a plan describes a tree that does not exist yet: an archive describes one that no longer does. Owner, 2026-09-02, choosing this over dropping the frozen rule so history could follow renames — the archive's whole value is that it does not change.
- DD-006: **Working memory must be tree-relative, because a cached world fact is a cache with no invalidation.** The state file asserted that the current version was untagged while its tag existed on origin, named a ledger volume's latest row three appends out of date, and claimed a forge protection setting no session can inspect — each true when written and read as current by every session after. `Current state` now records only what stays true of the checked-out tree; world-controlled status points at the live probe that recomputes it, an unresolved external action becomes an Owner-queue item with its command, and a retained past fact is scoped in the sentence to when it was observed rather than to a metadata field. The test is whether a sentence would survive this same commit being cloned tomorrow under another branch name. Prose-only and deliberately unguarded: the discriminator is meaning, so a rung grepping this file for forbidden phrases would be the attestation shape P3 refuses.
- DD-007: **A per-host shell fallback turns a missing prerequisite into a no-op, and a hook that returns 0 while doing nothing is the one broken-hook shape nothing reports.** Claude Code's hook shell form falls back to PowerShell on Windows when Git Bash is not discoverable, and a bare `.sh` path then goes to the Git for Windows file association, whose windowed launcher opens a detached terminal and returns 0 with no output — no `127`, no non-blocking-error notice, where every other failure of that layer is loud. All three shipped hooks now set the `shell` field to bash, inert wherever the adapter already works (each command is a path plus a literal argument, and each script names its own interpreter in its shebang) and loud where Bash is missing. What the pin does NOT reach, found by the rule-review pass rather than by the report: on Windows without Git Bash no Bash tool is registered and shell commands route through PowerShell, so the command guard's Bash-matcher hook never fires there at all and no shell value cures it, leaving the documented `Bash|PowerShell` remedy to the owner because the guard has no Windows-shell arm (**DC-027**). Reported 2026-09-09 from a Windows 11 host that HAS Git Bash, by running the adapter's command strings through PowerShell by hand rather than through the automatic fallback; the silent path also needs Git for Windows installed while its bash is undiscoverable, since that package owns both the association and the shell, and what a Bash-less host prints was never observed. The durable half: pin the interpreter a rail depends on, then check separately whether the rail is dispatched at all on the host you are hardening — a fallback that substitutes silently and a matcher that never fires look identical from inside a green tree.
  Corrected by DD-008.
- DD-008 [cited]: **The silent hook does not merely return 0 — it runs, unreachable, while the caller has stopped listening.** Emulating the fallback on the reporting host — the adapter's command strings through powershell.exe -NoProfile -Command with the hook JSON on stdin, not through the agent's automatic fallback, which a host that HAS Git Bash cannot trigger — the script executes detached beneath the association's windowed launcher, receives the new terminal's tty on stdin instead of the payload, and outlives a caller that has already moved on, so a guard reading stdin blocks forever in an unattended window and no exit code is ever consulted. The trigger is the file association alone rather than `PATH`, correcting DD-007: stripping Git from the child's `PATH` changed nothing, because the association does not consult it. An extension with NO association is not the loud case either — it raises the desktop's file-type picker while the harness still sees rc=0 and zero bytes, which is worse for a headless run, not better. The durable half: the caller saw nothing and nothing happened are different findings, and from inside a green tree a rail that fails by running where nobody is looking is indistinguishable from one that fails by never running.
- DD-009: **A pin that removes a silent failure can add one of its own, and the arm that would prove the trade is the one nobody ran.** Hook entries validate non-strictly: an unrecognised KEY inside one is dropped while the entry survives — the shape that would make a shell pin inert on a build predating the field — but a recognised key with an invalid VALUE drops the whole entry, so a typo in the pinned value removes a hook, a failure the unpinned config could not have. Where Git's bash is undiscoverable while WSL is present, bash may resolve to WSL's in another filesystem namespace, and whether the field resolves through `PATH` or a known Git location is undocumented. Unmeasured is the pinned arm itself: every measurement behind DD-008 is of the UNPINNED path, so that a pinned host with no discoverable Git bash fails loudly remains inference, and the single bash control run under a stripped `PATH` was loud only because that host has no WSL distro installed. The durable half: when a fix turns a silent failure into a loud one, the loud half is a claim about a host nobody has run, and a row that states the benefit flatly has smuggled the unmeasured arm past every later reader.
  Corrected by DD-010.
- DD-010: **The pinned shell is not resolved through `PATH`, so the WSL-misrouting hazard DD-009 raised does not exist.** The owner's Windows session reported this to this one on 2026-09-10, in session rather than in the issue thread: on a host whose registry `PATH` carries `Git\cmd` and no `bash.exe`, where `where bash` returns WSL's and a Store stub, a real pinned session ran its hook under Git's own bash and reported MSYS paths rather than WSL's `/mnt/c`, and did so again with every Git directory stripped from `PATH`. Reading the shipped bundle says why: discovery probes Git's default install location first, falls back to `git` on `PATH` and takes bash beside it, and honours an explicit override variable, so it consults neither `bash` nor `git` on `PATH` in the common case. How it fails when discovery finds nothing is version-dependent, and was read on a Linux machine rather than run on Windows: the 2.1.42 node bundle prints an instructive error and exits nonzero, while the 2.1.267 native binary returns no path and throws per hook, naming Git for Windows and the override variable. The durable half: a hazard reasoned from what a lookup command prints is a hypothesis about an implementation, and the two are one claim only when the implementation is that lookup.
- DD-011 [cited]: **A schema answers an unknown-key question that no amount of silence from an old binary can.** Whether pinning `shell` could disable a hook on a build predating the field was settled by reading the shipped hook schema at three versions: the command-hook object is non-strict, so an unrecognised key is stripped and the ENTRY SURVIVES, and the field is absent from 2.0.1 and 2.1.42 while present at 2.1.100 — so the pin is inert on a build predating it rather than fatal, and the same schema shows a recognised key with an invalid VALUE failing its enum and dropping the whole entry. Two runtime instruments were tried first and both died without saying so: an old build's checker crashed and its print mode rejected its own arguments, and only a control exercising the same path WITHOUT the key under test told a dead instrument from an inert key. The durable half: when the question is what a program ACCEPTS, the parser is primary evidence and an observed silence is not — and a negative run without a positive control through the same path reports the instrument's death as the answer.
- DD-012: **The command guard stays absent on Windows-without-Git-Bash rather than widening to a shell it cannot parse.** The documented remedy for a `PreToolUse` hook that never fires there is to match `Bash|PowerShell`; owner, 2026-09-10, in session rather than in the issue thread, declining it because the guard has no Windows-shell arm and a widened matcher would read PowerShell command text with a bash-shaped parser, buying coverage that looks real and is not. Revisit when that arm exists; the same decision declined a dangling-association experiment as not worth an uninstall on the reporting host.
- DD-013 [cited]: **A hand-applied hardening step that nothing checks is a step the next upgrade skips silently, and here it applies to the one file an agent is refused permission to edit.** 14.1.0's `shell` pin on the Claude adapter's hooks shipped as an Upgrading note with no rung behind it, so a tree with the step undone stays green and reads exactly like one with it done, and both typo shapes are quiet in the same way: a misspelled KEY is stripped leaving the entry unpinned, while an invalid VALUE fails the schema's enum and drops the whole hook entry (**DD-011**). `scripts/guards/adapter-set.sh` now requires the exact line `"shell": "bash"` under every `"type": "command"` entry in both the shipped template and the reference copy, and — since a line matcher speaks only for the layout it can read — counts the entries layout-independently and reconciles the two, so an entry it cannot read is reported UNVERIFIED rather than passed. Reported 2026-09-10 by a downstream adopter on Windows 11, who also found that auto-mode permission classifiers refuse every agent edit to the adapter settings file — that file defines the agent's own rails — so a human applied the step there, and an upgrade counting on agents to apply it would skip it with nothing reporting the skip. The durable half: a rail whose installation is manual needs a check for its ABSENCE, and that check has to live somewhere the agent is still allowed to write.
- DD-014: **A second host reproducing the file association's behaviour is not a second observation of the harness's own dispatch, however real the host is.** A downstream AMH 14.1.0 consumer on Windows 11 ARM64 measured `HKCR\.sh` to Git's windowed launcher and a probe exiting 7 with 18 bytes under `bash` returning rc=0 and zero bytes through the association, and concluded its host is exposed despite HAVING Git Bash on `PATH`; its own bounds section withdraws that, because it invoked the association's command line directly instead of unpinning the adapter and letting the agent dispatch — the arm **DD-008** already declined to claim, and discovery does not consult `PATH` anyway (**DD-010**). What it does add is a positive control nobody had: a pinned `PreToolUse` guard there passed its self-test and fired mid-session against a real Bash call, so pinned hooks demonstrably deny on Windows — on a second host where discovery SUCCEEDS, leaving the discovery-fails host still unrun. Its reading of the cost is right and already shipped: the script runs and only the verdict is destroyed, so a guard signalling deny by non-zero rc has its block silently downgraded to an allow (**DD-008**). The durable half: when a field report's headline is broader than the arm it ran, its bounds section is the finding — update on the control it added, not on the conclusion it drew.
- DD-015: **An adapter sentence saying the host cannot do something is a capability claim with an expiry date, and nothing here was watching it.** P17 has required output-filter piping since it was written, and the Claude adapter's "this agent has no output-filter hook" was true when authored and false by the time an external RFC pointed at it — `PostToolUse` returns `hookSpecificOutput.updatedToolOutput`, which replaces the result the model reads — so wiring `scripts/redact-tool-output.sh` is conformance to a rule that already bound, not new machinery the incident bar governs. The layer's own bounds ship in the adapter prose rather than waiting to be discovered, because every one of them is invisible from a green tree: the host discards a replacement that misses the tool's response schema and uses the original output, the event fires on SUCCESSFUL tool calls only, the value already exists in the tool's execution and the transcript, the filter catches enumerated shapes and no more, and a missing `python3` stands the whole rail down. That last one needed the report as well as the prose: `REQUIRED_TOOLS` now names `python3` so the session banner says whether it is there, because a sentence claiming the banner reports a tool it was never given is the enforcement-asymmetry class rather than a detail. The durable half: a capability claim about someone else's product is the one kind of documentation that rots without any change to this repository, and the fix is to state what the layer does NOT reach in the same breath as what it does — an adapter that understates its layers misleads exactly as much as one that overstates them.
- DD-016 [cited]: **A filter with cross-line state cannot be batched, and the acceptance rule that was supposed to catch the corruption was the one thing the corruption satisfied.** Filtering every string leaf of a tool response in ONE `redact.sh` invocation, separated by a generated marker line, let that filter's private-key stage — a sed line RANGE — stay open past an unterminated BEGIN marker in one leaf and rewrite every later leaf, where its body pattern matches any all-base64 line: ordinary single words and most slash-only paths. A measured Read response came back with `filePath` replaced by a redaction marker, published under a message asserting a redaction, and the guard against exactly this — accept a changed leaf only if it CONTAINS `[REDACTED:` — passed it, because the corrupting substitution genuinely adds one. Two fixes, and the second is the subtler: filter per leaf so each leaf's range state is its own, and COUNT markers instead of testing for one, since a leaf that already carried that literal — common here, where this filter's own output and this repository's prose both contain it — was otherwise accepted on any byte change, including the CRLF rewrite that is the whole reason the rule exists (**DC-030**). Found by the mandatory fresh-context pass after the author had reasoned the cross-leaf case was safe because over-redaction is the safe direction; it is not safe, because over-redaction of a DIFFERENT field is corruption, and the author's own header claimed the case was closed. The durable half: "the safe direction" is a property of what a rail does to the thing it was aimed at, never of what it does to everything else in the same buffer — and a precondition that the failure mode itself satisfies is not a precondition, which is why each of these rules now ships with a fixture that fails against the shape it replaced.
- DD-017 [cited]: **A shared hook entry point must translate host response contracts, not merely accept their common input.** Codex PostToolUse supplies the same `tool_response` shape the Claude redactor consumes but does not accept Claude's arbitrary `updatedToolOutput`; returning it fails open and exposes the original. The Codex adapter therefore blocks only a result that actually gained a redaction marker and supplies the filtered value as model feedback, accepting the narrower costs that the tool looks failed and structured output becomes JSON text rather than claiming an in-place rewrite the host does not perform.
- DD-018: **An advisory that clears on a rerun is aimed at the wrong end of the destructive tier's range, and the shape that actually destroys a machine never reaches a command scanner at all.** A public report described an agent asked to add a delete feature: it wrote a safety guard, deleted the guard from the source to demonstrate the guard was necessary, ran the test against a live path, and `shutil.rmtree("/")` took the repository, the home directory, SSH private keys and a GPG keyring. Measured against this repository's own rails, the bash spelling was a one-time advisory a rerun clears — `/` carried byte-identical text to `build/` — and the interpreter spelling, the test-suite invocation and `find / -delete` returned rc=0 in silence. Two fixes, deliberately unequal: a literal, tiny target list (`/`, the home directory in its variable and live-value spellings, `/root`, `/home`, `/Users`, and the trailing and glob forms that fold to them) is now the guard's ONE permanent denial, decided before the state file is touched so the promise does not rest on a temporary file; and the constitution gained the rule the scanner cannot hold — exercise an unguarded destructive path against a fixture, never a live one, and never remove a safety check to observe what it prevents. The second half was the uncomfortable one, because the add-a-guard playbook already required demonstrating that a fixture fails without its behaviour, and the incident is what that instruction looks like when an agent applies it to the real filesystem instead of the suite. The durable lesson: the advisory tier's premise is that the agent's rerun settles intent, so where intent cannot be in question a rerun settles nothing and the tier is the wrong instrument — and widening a verb list is never the answer to an interpreter, which has unbounded ways to spell the same deletion.
- DD-019: **A rail that must read program text can be built, but only when the licence to look comes from the COMMAND — and each narrowing is worth more than the tier it enables.** The interpreter hole documented since **DB-010** stayed open because closing it seemed to require judging program text, which this guard's first design rule forbids: a commit message or a doc line containing `shutil.rmtree("/")` must never be judged, and a repository whose own rails cannot describe themselves is the failure that rule exists for. Three narrowings resolve it — the segment's LEADING command is an enumerated interpreter, the segment carries an inline-code flag, and THAT FLAG'S ARGUMENT names a deletion call before an opening parenthesis — and the mandatory review found the first form had only the first of them, so matching ran over the whole segment and advised a pytest run whose test file was named after a deletion, a pure READ of a documentation file whose name carried the same word, and the identifier `unlink_count`: a repository that has deletion code is precisely the one whose files are named after it. What the tier buys is one turn, not coverage, and it says so: the advisory clears on a rerun, rearms per command, and states that a script file, a test suite, a heredoc body, `bash -c` and `os.system("rm -rf /")` all pass it unjudged. It also states the asymmetry rather than leaving it to be discovered — `rm -rf /` is denied permanently while the same deletion spelled inline clears on a rerun, not because the interpreter spelling is safer but because program text cannot be judged well enough to deny on. The durable half: when a guard cannot judge a category, ask what narrower FACT about the command licenses a look, then test each narrowing against the repository that would actually run it, because the false positives of a text-matching rail land hardest on the codebase the rail is about.

- DD-020: **A rail's own bookkeeping is subject to the secret rules it exists beside, and a quoting primitive can turn an advisory into a permanent lockout.** This tier first keyed its rearm on `printf %q` of the whole command, which wrote a `python3 -c` program verbatim into a world-readable, predictable, session-outliving `/tmp` file — the one place a literal credential in a one-liner would come to rest, in a repository whose constitution forbids exactly that disclosure — and `%q` renders an embedded newline as a backslash-newline on bash before 4.4, which this file still supports, so a multi-line program would have produced a two-line signature that `grep -qxF` can never match and a command that could never be rerun. Hashing the newline-flattened command closes both, and the absence of any digest tool is answered by re-advising rather than by recording something unkeyable. Two fixtures hold it: the state file must not contain a planted fixture secret, and it must be exactly one line. The durable half: when a rail writes anything down, ask what its file would contain on the worst day rather than the average one, and treat a quoting helper's platform variance as a correctness property whenever its output is later matched exactly.

- DD-021: **Editing the rail that gates your own commands means a syntax error takes the shell away, and the recovery is a path that does not go through the hook.** A stray backslash-quote inside a single-quoted advisory string left `scripts/command-guard.sh` unparseable; because the harness runs that file as its pre-execution hook, the next Bash call — including the one that would have fixed it — was refused with the parse error, and a session that could only edit through the shell would have been stuck. The editor tools bypass the hook and repaired it in one step. The cheaper lesson is upstream: validate the TEMPLATE with `bash -n` before copying it down, so a broken copy never reaches the path the hook executes.

- DD-022: **A guard's diagnostic is bound by the rule the guard enforces.** The author-identity rung printed every address it rejected, defended in its own comment because the address was already in commit metadata, while the constitution forbids rendering an unapproved address and a rejected one is unapproved by definition. It now names the field, the commit and the reason, and a fixture feeds every rejecting arm a marked address and fails if any marker reaches the output. When a guard exists to keep a value out of view, audit each of its failure lines against that same rule, because a diagnostic travels into logs and transcripts that the artifact it inspects never reaches.

- DD-023: **What a guard chooses to look at, and the recovery it advises, can be narrower or wider than its comment says, and a green verdict reveals neither.** One external review found three: the new-row length rung discovered changes with `git diff HEAD`, which omits untracked files, so a new ledger volume or a never-committed base ledger went unmeasured and its rows became exempt history on commit; `git fetch origin <branch>` exits 0 without creating the remote-tracking ref when the clone's refspec does not map it, so the advice the metadata rungs printed, and this repository's own warm-up, could leave those rungs inert; and a `case` glob's `*` crosses `/`, so the bare `~name` arm permanently denied `~name/sub`. Each fix ships with a fixture on the input that was missed or over-matched, the fetch fixture running the advice in a real single-branch clone. Test the selection and the advice, not only the verdict.

- DD-024: **An installer that keeps a user-owned configuration must render everything it writes from that kept file, read the way its consumers read it, and must check a kept value only where it is about to write it.** `amh-init.sh` kept an adopter's `amh.conf` but rendered newly written adapters from its own options and defaults, so a repository installed with `master` and upgraded without repeating the option got static Codex rules protecting `main` while every dynamic guard read `master`; its validation also protected only the `sed` substitution, so `release/"stable"`, a valid git branch name, produced adapter JSON that did not parse. It now sources the kept file from the target's root as the shipped scripts do, refuses a disagreeing option and a file that does not load to its end, and narrows branch names to characters every grammar they reach reads literally. The first draft of the fix checked every kept value and so refused upgrades over values no written file carried — a check must reach only what the run is about to write, or it blocks an adopter's working tree for nothing.

- DD-025: **A command substitution used as a command's argument discards its status, so a generator can succeed on a tool that failed.** `build-manifest.sh` printed `"$(sha256_of "$f")"` inside `printf`'s arguments, so a hasher that exited non-zero cost nothing under `set -e` and the run wrote empty digests over both manifests. Each digest is now captured and checked for shape before it is printed, the run stops non-zero in both modes, and neither manifest is replaced until the whole file has been built; a fixture with a failing hasher asserts both modes fail and the committed pair is unchanged.

- DD-026: **The 2026-09-29 external review of the 15.0.0 draft was validated finding by finding against the tree, and all fifteen findings held.** They were fixed in three units: shipped scripts (**DD-022**, **DD-023**), the installer and manifest generator (**DD-024**, **DD-025**), and prose and policy (**DD-027**–**DD-029**). One was adopted in substance but not in mechanism: a Codex prefix rule cannot express "and nothing after", so its stricter `env`/`set` behaviour is documented beside the rule rather than aligned with the command guard. The fixes' own reviews surfaced one older defect, the permanent denial's `*/` fold, which went to the Owner queue rather than into the unit that found it.

- DD-027: **A checkpoint that validates before its last edit verifies a tree nobody commits, and a check that reads commits cannot see the commit made after it.** The sequence ran the ladder, then wrote the state-file line, then committed and pushed, so the committed tree always differed from the verified one, and the poison-token and author-identity rungs, which read `origin/<default>..HEAD`, never saw the commit about to be published; the pre-push rail judges refs only, and a disposable repository accepted a fast-forward carrying a new `[skip ci]` commit. The sequence is now state-file line, ladder, commit, `--guards-only` again, push, in the constitution, both runbooks, P5 and the seed, and applying review findings re-runs the ladder before the commit because it changes the tree again. Order a checkpoint so each check runs after the last change it can see and before the step it protects, and read a check that WARNs it compared nothing as one that did not run.

- DD-028: **A correction to the reference constitution reaches no adopter until the seed carries it, and nothing checks that it does.** Seeds are copied once and never drift-checked, so the reference's does-versus-should limit on "trust the code" and its pre-push exception to "a hook-less agent has only prose" had never reached `harness/templates/seed/`, and the seed ledger promised a path check only this repository runs. The runbook's seed playbook now says to search the seed in the same change whenever a unit corrects a rule it restates, and to route any difference through the CHANGELOG's Upgrading notes.

- DD-029: **Squash-merging destroys the inside of a train, not the evidence of what each merge delivered.** **DA-003** generalised a real failure into "`git log` cannot answer a question about this repository's past" and "the only surviving record", and the runbooks, the seed and the session banner repeated it; but merged snapshots and the diffs between them survive and are evidence. What squashing removes is the intermediate commits — which session did what, in what order and why — and what no log search can establish is that something never happened, which is the claim the original failure made. The ledger and the STATE changelog remain the record for those questions, which is the part of **DA-003** that stands.

- DD-030 [cited]: **A name on PATH is not a working interpreter, and a bare program name handed to a native Windows process is resolved through System32 before PATH; either one alone produces the same silent failure, so the log could not say which fired.** The train's first Windows CI run failed six self-test checks of the redaction hook, every one a check that needs output; replayed on Linux, a `python3` that exists and does not run (the Store alias's shape) and a bare `bash` that resolves to the wrong shell each reproduce those six exactly, and neither cause was observed on the runner. The hook now accepts `python3`, then `python`, only after running it as Python 3, and hands its walker this shell's own path with `.exe` spelled out; `command-guard.sh`, which read a non-running `python3` as "no command in this payload" and allowed every Bash call, now falls back to its bash parser instead; and CI prints which interpreter and `bash` the Windows leg resolves. The same run exposed that the ladder printed `ok` for a self-test that SKIPped, which it now reports as `skip` with its reason. When two hazards explain one failure, fix both and record neither as the cause until something observed it.
